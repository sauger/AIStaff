# 员工企微通知绑定

## 交付范围

员工通知绑定及其通知基础服务支持：管理员从已识别的私聊联系人中显式选择；员工本人用一次性码认领；解绑、重新绑定、测试通知、状态展示；按企业人员 ID 解析接收人并写入现有 outbox。

**ITO 业务配置和阶段完成事件尚未接入。** 未修改账单技能、提示词、邮件收件人，也未重发邮件。业务接入时调用下述服务，不应把会话 ID 或企微外部地址写入业务配置。批量通讯录同步仍不在本次范围内。

## 使用入口

- 管理员：企业管理 → 组织架构 → 点击员工或编辑员工；也可在企业管理 → 成员 → 编辑企业人员。已保存的员工档案下有“企微通知”。
- 员工本人：企业管理页面或数字员工广场右上角头像 → 我的企微通知。需要既有 `primary_user_id` 关联到本人登录账号；没有网页登录账号的员工可以由管理员绑定。
- 选择机器人及企业范围，再选择已识别的私聊成员。选项展示姓名、成员 ID、企业范围，不按姓名匹配。目录导入的 UserID 不能代替机器人私聊证据。
- 自助认领使用 `/通知绑定 <码>`，与已有的 `/绑定` 登录改挂命令分开。只有指定租户、人员、企业范围和机器人可消费，十分钟有效，新码使旧码失效，只保存码的 SHA-256 摘要。
- “已绑定”默认仍为“未验证”。测试通知需渠道适配器实际接受才显示成功，不提供已读状态。页面投递等待中会刷新状态。

## 数据流与权限边界

```text
认证用户 → 管理员显式选择 / 本人私聊认领
          ↓
EnterprisePerson.id → person_notification_bindings → PersonContact（合并链规范化）
          ↓                         ↓
有效人员、身份冲突检查       企业范围 + 机器人账号稳定键 + 私聊成员 ID
          ↓                         ↓
                  精确匹配有效私聊会话
                            ↓
ChannelDelivery(kind=person_notification，目标快照，业务幂等键)
                            ↓
outbox 发送前重新校验人员、通知关联、联系人、机器人、来源员工和会话
                            ↓
                    现有企微机器人适配器
```

新增 `person_notification_bindings` 和 `person_notification_codes` 两张附属表。人员、渠道身份继续以现有人员和联系人为准，不写旧 `channel_identities`，不改主账号、网页登录关联、审批身份。绑定表记录明确选择的通道及身份快照；已撤销行保留创建人、撤销人及时间。活跃人员和联系人分别有唯一索引，写入按现有 SQLite 写锁串行化。

复用 `org/wecom_link.py` 的既有身份冲突检查，不调用其主账号选择或改挂方法。机器人使用明确企业范围；尚未配置企业 ID 时，仅接受已验证机器人独立范围，并明确显示“当前机器人范围（未配置企业 ID）”。联系人范围、私聊成员、绑定账号不一致时拒绝。不会回退到其他机器人、任意最近聊天或群聊。合并后身份发生变化需要重新绑定。

普通员工只能读取、测试、解除本人的通知绑定、生成本人的认领码；选择联系人关联的管理接口只允许管理员。所有入口均检查租户。

## 业务通知调用

`app.org.notifications.stage_notification` 是服务端内部业务事件入口，不开放任意外部收件人 HTTP 接口，也未添加允许模型自由填写收件人的工具。

参数：`tenant_id`、`recipient_person_id`、`source_agent_id`、`event_key`、`text`。调用方先完成业务事件授权，随后与业务状态在同一事务提交；返回 `ChannelDelivery`，业务执行记录应保存其 `id`。来源数字员工必须属于租户、有效且挂载到通知机器人。

`event_key` 应由业务确定，例如流程实例、阶段、事件版本；服务还把租户、来源员工、接收人员纳入幂等键。重复事件返回原投递，不重复发送。重新绑定后同一个业务事件仍返回旧记录，不会静默换接收人；确认需重新发起时由业务使用明确的新事件版本。

消息限制为 1700 UTF-8 字节，避免适配器拆分长消息带来的部分成功。企微机器人不能传入远端去重键，因此发送异常或恢复一个可能已经发送的任务时不会盲目重试。渠道离线等发送前失败会明确返回原因。

解除或重绑立即终止旧关联的 pending 消息；已领取的消息在发送前再次校验。已经进入远端发送的消息无法撤回。人员停用、来源员工停用、通道账号变更或会话失效也会阻止后续发送。历史投递记录保留。

## SQLite 发布与回退

本次无既有表 ALTER，无人员或账号数据回填。应用启动时的 `SQLModel.metadata.create_all` 创建新表和索引；重复启动安全。

部署前：停止应用及渠道 worker，使用 SQLite 的在线备份接口或 `sqlite3 <实际数据库路径> '.backup <备份路径>'` 做完整备份；确认备份可读，再部署前后端并启动。不要仅复制处于 WAL 写入中的主文件。这里的路径应由实际部署配置获取。

回退前：停止应用及 worker。旧版本 outbox 不认识新增校验，因此应先在数据库备份后将未完成的新通知终止，再回退程序：

```sql
UPDATE channel_deliveries
SET status = 'failed', last_error = 'notification feature rollback',
    next_attempt_at = NULL, sending_since = NULL, delivery_owner = NULL
WHERE kind = 'person_notification' AND status IN ('pending', 'sending');
```

保留新增两表作为审计历史，旧代码不会使用它们；无需删除表或清除业务记录。如需完整数据库回退，只能使用部署前备份，并评估备份之后新增业务数据的损失。恢复新版后不得把结果不明的历史投递直接改回 pending。
